= Quickstart
:description: Generate OpenAPI from endpoints in the current module or from a compiled API dependency.

This guide shows how to generate an OpenAPI document with Maven. For Gradle, see the
xref:gradle-quickstart.adoc[Gradle quickstart].

The examples use the `example-contract` and `example-application` modules in the tapik repository.

== Requirements

* Java 25
* Kotlin 2.4 or newer
* Maven 3.9+ or Gradle 9.1 through 9.8

== Generate OpenAPI in the API module

Use this when the current Maven module defines the APIs. The compiler first records them in a registry, so generation
runs later in the same lifecycle at `process-classes`.

</dependencies>
----

=== 2. Enable registry generation

Add tapik to `kotlin-maven-plugin`. The compiler plugin records the module's public `Api` declarations in a registry.
The generation plugin reads the registry; it does not search project classes for APIs.

[source,xml]
----

----

----

=== 4. Configure the OpenAPI target

Add one execution of the same tapik Maven plugin. Omitting `<phase>` is intentional: the `generate` goal defaults to
`process-classes`, after the current module and its registry have compiled.

[source,xml]
----
include::example$contract/pom.xml[tag=same-module-openapi]
----

=== 5. Run the lifecycle

From the tapik repository, the smallest command that reaches that execution is:

[,shell]
----
./mvnw -pl example-contract -am process-classes
----

The generated document is:

[,text]
----
example-contract/target/generated/tapik/Books.openapi.yml
----

In your own standalone project, run `./mvnw process-classes`. `./mvnw compile` is too early for a same-module
execution, while `package`, `verify`, and `install` all include `process-classes` and therefore also generate the file.

== Generate from a compiled API dependency

Use this workflow when an application depends on an API module that has already compiled. Its registry is available,
so generation can run during `generate-sources`. Choose this when application code needs generated client or server
types.

First, depend on the API artifact:

[source,xml]
----
include::example$application/pom.xml[tag=compiled-api-dependency]
----

Then bind the target execution explicitly to `generate-sources`:

[source,xml]
----
include::example$application/pom.xml[tag=compiled-api-dependency-openapi]
----

The runnable reactor example can be built with:

[,shell]
----
./mvnw -pl example-application -am compile
----

`-am` builds the API module first. Outside a reactor, publish the API artifact to a Maven repository or install it
locally before compiling the application. The document is written to:

[,text]
----
example-application/target/generated/tapik/Books.openapi.yml
----

== Choose the lifecycle phase

[cols="2,2,2,2", options="header"]
|===
|Where APIs are declared |Execution phase |Minimum command |Can main source use generated Kotlin?

|The current module
|`process-classes` (default)
|`./mvnw process-classes`
|No; main compilation has already finished

|A compiled dependency
|`generate-sources` (explicit)
|`./mvnw compile`
|Yes
|===

Only these two execution bindings are supported; later lifecycle commands such as `package` and `verify` reach them
normally. Running `./mvnw tapik:generate` directly is not a substitute for a fresh lifecycle build: it requires existing
compiled output and API registries, runs no user compilation, and performs late compilation of generated Kotlin.
See xref:reference/maven.adoc#_direct_invocation[direct invocation] for configuration and stale-output caveats.
During generation, tapik logs every file it writes, making the selected APIs and output locations visible in the build.

The default artifact output is `${project.build.directory}/generated/tapik`. Source targets in the runnable application
use one explicit shared directory:

* Spring RestClient and WebMVC: `target/generated-sources/tapik-spring`
