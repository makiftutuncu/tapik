= Generate OpenAPI
:description: Produce OpenAPI 3.2 documents from tapik API values.
:page-aliases: generation/openapi.adoc, code-generation/documentation.adoc

The `openapi` target converts each selected API into one OpenAPI 3.2 document. OpenAPI is generated output, never the
contract source: change the Kotlin API and regenerate rather than editing the document.

== Before you start

The module that declares an API must enable tapik's Kotlin compiler plugin so its compiled artifact contains an API
registry. Body formats must provide schemas for values that OpenAPI needs to describe. The runnable contract uses the
Jackson integration:

----
include::example$contract/Books.kt[]
----

This definition supplies the method, path, success status, JSON media type, and derived `Book` schema. The target uses
the API ID as the document title and the endpoint ID as `operationId`.

== Generate beside the contract

Documentation does not need to be compiled into application source, so same-module generation is the shortest setup.
Configure an `openapi` execution without a phase; the goal's default `process-classes` phase runs after the current
module and its registry exist:

[source,xml]
----
include::example$contract/pom.xml[tag=same-module-openapi]
----

Run a lifecycle that reaches `process-classes`:

[,shell]
----
./mvnw -pl example-contract -am process-classes
----

The example produces one default YAML document for each registered API:

[,text]
----
example-contract/target/generated/tapik/Authors.openapi.yml
example-contract/target/generated/tapik/Books.openapi.yml
example-contract/target/generated/tapik/Catalog.openapi.yml
----

`compile` alone is too early in this mode. `package`, `verify`, and `install` also reach the configured execution.

== Generate from a contract dependency

An application can instead depend on an already compiled contract and bind the same target to `generate-sources`.
This is useful when documentation belongs to a consuming or publishing module, although OpenAPI itself does not need
the early phase. The xref:getting-started.adoc#_generate_from_a_compiled_contract[compiled-contract quickstart] shows
the complete dependency and execution.

== Select and name documents

By default every visible API gets its own document. `includeApis` and `excludeApis` can select exact API IDs, while the
target's `output` template controls the relative path. This tested execution includes `Authors` and `Catalog`, excludes
`Authors`, and therefore writes only `filtered/Catalog.yml`:

----
include::example$application/pom.xml[tag=api-selection]
----

YAML with a `.yml` extension is the default. Set `format` to `json` for JSON, use `pretty` to control JSON formatting,
and choose `simple` or `qualified` component naming. The `version` option is required and becomes `info.version`.
See xref:reference/generation-options.adoc#_openapi[OpenAPI target options] for the complete table.

== What the target translates

The target preserves endpoint declaration order and interprets the contract's paths, methods, parameters, headers,
request bodies, response alternatives, media representations, schemas, tags, and documentation. Schema references
become reusable components. Optional and repeated query shapes, defaults, fixed values, unions, discriminators, and
deprecation metadata are represented where OpenAPI supports them.

Generation fails for unsupported mappings—for example, when schema references cannot be resolved,
two endpoints become the same OpenAPI path and method, or a wildcard remaining path has no faithful representation.
The diagnostic identifies the relevant path, component, or endpoint.

Named reference aliases remain separate components when their normalized names differ. Discriminated unions must
provide `defaultMapping` if any alternative does not require the discriminator property; the target checks this after
resolving schema references. Discriminators are selection hints: the underlying schemas must still distinguish the
alternatives correctly.

== Current coverage boundaries

OpenAPI 3.2 is the output version, not a claim that every OpenAPI feature has a tapik DSL equivalent. Servers, security
schemes, callbacks, webhooks, links, examples, rich tag metadata, and extensions are not modeled yet. Nor are
multipart/form encodings, streaming item schemas, or XML-specific schema metadata.

Headers are translated literally. OpenAPI tooling may ignore request `Accept`, `Content-Type`, and `Authorization`
parameters and response `Content-Type` headers; header declarations do not create security schemes. Define body
media types through body formats. Unlike request bodies, OpenAPI responses have no body `required` flag, so an
optional response body documents its possible media types without representing absence as JSON `null`.

== Ownership boundary

You own the Kotlin APIs, models, format configuration, documentation, and the Maven execution. tapik owns generated
documents below the execution output directory. They may be validated, packaged, or published by later build steps,
but hand edits will be replaced on regeneration.

Continue with xref:reference/maven.adoc[Maven reference] for lifecycle and selection behavior or
xref:reference/troubleshooting.adoc[Troubleshooting] when generation fails.
