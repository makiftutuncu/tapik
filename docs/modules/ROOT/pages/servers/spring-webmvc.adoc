= Generate a Spring WebMVC server
:description: Generate pure server interfaces and automatically registered Spring WebMVC controllers from tapik contracts.
:page-aliases: generation/spring-webmvc.adoc, code-generation/server.adoc

The `spring-webmvc` target turns each selected API into two deliberately separate responsibilities:

* a pure Kotlin `Server` interface implemented by application handlers;
* an internal generated Spring controller that owns mapping annotations, wire conversion, and delegation.

This separation keeps user behavior free of Spring HTTP details and lets future server targets place another framework
adapter around the same contract information.

== Use a compiled contract

The application must implement generated interfaces in its ordinary Kotlin source, so generate from an already
compiled contract during `generate-sources`. Add the contract, WebMVC target runtime, and Spring Boot WebMVC starter.

`BooksGeneratedController` adapter.

== Implement the handler

The generated interface exposes the original API value, one abstract method per endpoint, and a sealed response type
for each method. The user-owned handler deals only with decoded Kotlin inputs and typed outputs:

`BooksHandler` has no mapping annotations, `ResponseEntity`, encoded bytes, content negotiation, or adapter bean
configuration. A more complex endpoint would expose path variables, query parameters, headers, and a decoded body as
method parameters. The handler chooses one generated response alternative and supplies its body and headers.

== Let Spring Boot register the controller

`tapik-target-spring-webmvc` publishes Spring Boot auto-configuration through Spring's standard
`AutoConfiguration.imports` resource. On startup, the auto-configuration reads tapik's generated adapter descriptors,
finds a handler bean for each generated `Server` interface, and registers the matching internal controller bean. This
is deterministic descriptor discovery, not package scanning of APIs or controllers.

The example only needs an ordinary Spring Boot application and the `@Component` handler shown above:

[source,kotlin]
----
include::example$application/LibraryApplication.kt[]
----

For a server interface, registration uses the sole matching handler bean. If multiple beans implement it, mark exactly
one `@Primary`; with no unambiguous handler the corresponding controller is not registered. One handler bean may
implement several generated server interfaces and receive a controller adapter for each one.

== Use plain Spring

In a non-Boot Spring application, annotate a configuration class with
`@dev.akif.tapik.target.spring.webmvc.EnableTapikWebMvc`. It activates the same descriptor registrar and bean-selection
rules. The annotation registers generated adapters only; it does not enable or configure Spring WebMVC itself.

== Request and response boundary

The internal controller owns routes and Spring mapping annotations. It decodes path, query, and header strings with the
contract formats, validates required and fixed inputs, selects request-body media representations, and calls the
handler with Kotlin values. It converts decoding and media-type failures into the appropriate HTTP response before the
handler is invoked.

After the handler returns, the controller matches the selected response alternative, encodes its body and headers,
negotiates the response representation, and constructs the Spring response. The handler cannot return a status or body
shape outside the generated sealed hierarchy.

== Ownership and naming

tapik owns the generated `Server` interface, internal controller, registration descriptor, and wire conversion. Your
application owns handler behavior, Spring bean annotations, dependencies, persistence, transactions, authorization,
and other application policy.

The defaults are `dev.akif.tapik.generated`, `Server`, and `GeneratedController`; all three are configurable. See
xref:reference/generation-options.adoc#_spring_webmvc[Spring WebMVC target options]. Use the compiled-contract layout
when the current application's handlers need to implement generated interfaces; same-module generation happens after
its ordinary source compilation.

Continue with xref:reference/troubleshooting.adoc#a_spring_handler_is_not_found[Spring handler troubleshooting] if a
mapping is absent at runtime.
