= Type safety
:description: Learn how tapik keeps endpoint details in Kotlin types and checks definitions before runtime.

tapik keeps each endpoint's path, query parameters, headers, request body, and responses in the Kotlin type inferred
from its DSL. Adding one of these details changes the type; tapik does not flatten endpoint definitions into a separate
metadata model.

== Where checks happen

Kotlin compilation:: The DSL does not let you make a path value optional, add a second request body, or add a path
after query parameters. The Kotlin compiler rejects these definitions.
Endpoint creation:: tapik rejects duplicate parameter names and overlapping response status matchers when it creates the
endpoint value.
Output generation:: An endpoint with a remaining-path wildcard is valid, but OpenAPI cannot represent it. Spring
WebMVC cannot map `CONNECT` or `QUERY`; the RestClient target accepts both, subject to the configured transport. The
selected target reports unsupported endpoint features.

You normally do not write these types yourself. Kotlin infers them from the endpoint definition.

See the xref:endpoints/uris.adoc[URI guide], xref:endpoints/requests.adoc[request guide],
xref:endpoints/responses.adoc[response guide], xref:documentation/openapi.adoc[OpenAPI guide], and
xref:servers/spring-webmvc.adoc[Spring WebMVC guide] for these rules in context. See the
xref:clients/spring-restclient.adoc[Spring RestClient guide] for client behavior.

An endpoint that passes Kotlin and tapik validation may still use a feature unsupported by a selected target. OpenAPI
is generated output; tapik does not use it to reconstruct endpoints.
