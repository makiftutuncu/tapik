= Type safety
:description: Learn how tapik keeps endpoint details in Kotlin types and checks definitions before runtime.

tapik keeps each endpoint's path, query parameters, headers, request body, and responses in the Kotlin type inferred
from its DSL. Adding one of these details changes the type; tapik does not flatten endpoint definitions into a separate
metadata model.

== Where checks happen

[cols="1,3,3", options="header"]
|===
|Stage |Example |When tapik reports the problem

|Kotlin compilation
|A second `.input(...)` call, an optional path value, or a path added after query parameters.
|The Kotlin compiler rejects the definition before it produces an endpoint value.

|Endpoint creation
|The same path-variable name used twice, or two output alternatives with matchers `Status.Ok` and
`statusesIn(200..299)`. Both match status 200.
|tapik rejects the duplicate or overlap while building the endpoint value.

|Target generation
|A path ending in `remaining("tail")` passed to OpenAPI. Spring WebMVC also cannot map `CONNECT` or `QUERY`.
|The selected target reports the unsupported feature. The RestClient target accepts `CONNECT` and `QUERY`, subject to
the configured transport.
|===

You normally do not write these types yourself. Kotlin infers them from the endpoint definition.

See the xref:endpoints/uris.adoc[URI guide], xref:endpoints/requests.adoc[request guide],
xref:endpoints/responses.adoc[response guide], xref:documentation/openapi.adoc[OpenAPI guide], and
xref:servers/spring-webmvc.adoc[Spring WebMVC guide] for these rules in context. See the
xref:clients/spring-restclient.adoc[Spring RestClient guide] for client behavior.

Passing Kotlin and tapik validation does not guarantee that a selected target supports every feature. OpenAPI is
generated output; tapik does not use it to reconstruct endpoints.
